# 上下文与工具 Token 容量分析

统计日期：2026-10-04。数据来源：手机现有历史数据库的只读副本、最新模型请求快照，以及仓库内 MCP 接口文档。本文只保留聚合统计，不包含原始对话、家庭地址、坐标、照片、订单标识或密钥。

配置更新（2026-10-04）：已按用户确认将全输入工具清理软阈值设为 **64,000**、清理目标 **48,000**；文字仍为 **16,000/8,000**，最近轮次保护与硬边界不变。下文 32K 分析及请求快照保留为调整前的测量基线，64K 容量估算见第 4 节。

## 结论

32K 对时间、定位、地址解析等轻量工具比较宽裕，但对于保留多轮完整打车预估或公交路线结果偏小。决定容量的主要因素不是工具数量，而是返回结果大小。

- 常驻 15 个工具定义：**2,560 个保守估算 Token**。本次系统提示词（含用户常用信息）另占 1,024；固定基底加全局开销约 **3,712**。常用信息改变后，基底会随之变化。
- 单次时间查询约 **101**，地址解析约 **198**，驾车路线约 **1,450**，公交路线样本约 **7,625**，打车预估约 **8,029～22,817**。这些是调用参数、结果和消息封装合计，不是只有返回值。
- 以一轮约 150 Token 的文本为例：32K 在预算内能容纳约 **46 轮轻量三工具查询、14 轮驾车路线查询、3 轮公交查询，或 1 轮较大的打车预估**。这是场景估算，不是实际轮数上限。
- 16K 是独立的历史文字阈值，不包含工具定义和工具结果；现有短对话样本每轮纯文本平均约 118 Token，约 **135 轮**触发，卸载到 8K 后约留 **67 轮**。若每轮长到 500 Token，则约 32 轮触发、目标约 16 轮。
- 初次统计没有改动参数；随后已将 32K/24K 更新为 64K/48K，16K/8K 保持不变。没有新建或取消任何打车订单。

## 1. 统计口径与可信度

本次有 25 个历史会话、58 轮用户输入、60 次工具结果、11 张图像事件。60 次调用全部正确配对，覆盖 13 种工具。样本是开发与实际使用的混合数据，不代表未来使用分布；公交、定位、订单查询等只有 1 次样本，不能视为该接口固定大小。

区分三件事：

1. **工具定义成本**：名称、说明、完整 JSON Schema。常驻工具每次请求都带上；发现的新工具加载后会继续随会话发送，不是只在调用那一次发送。
2. **单次调用新增成本**：assistant 中的调用名称/ID/参数 + tool 返回结果/ID + 消息封装。下一次请求会再次发送仍在模型视图里的旧调用链。
3. **真实请求用量**：DeepSeek 返回的 `usage.prompt_tokens` 是整份输入，`completion_tokens` 是本次模型输出（包括模型产生的工具调用参数），`total_tokens` 是两者相加。它不是“整段会话只计费一次”的统计；工具服务器返回内容会计入后续模型输入。

### 本地估算

复现目前 Kotlin `ConservativeTokenEstimator` 的规则：ASCII 字符 × 0.4、汉字 × 0.8、其他码点 × 1.0，再加 15% 余量并按字段向上取整；每个定义额外 24，每个调用额外 16，每条模型消息额外 12，全局额外 128。不是精确 tokenizer。并行调用共享 assistant 消息，表中按每调用独立分配该消息的 12 Token，因此略偏保守。

DeepSeek 官方给出的普通文本经验值为英文字符约 0.3 Token、中文字符约 0.6 Token，并强调实际以 API 返回为准。JSON 的数字、标点和字段名分词不同，不能用统一字符除数做精确换算。[官方 Token 用量说明](https://api-docs.deepseek.com/zh-cn/quick_start/token_usage/)

表中历史调用链是**未卸载的完整内容**，不是旧策略裁切后的请求，也不是整个 MCP HTTP 包。非模型输入的 GPS/时间元数据不计入。估算使用校准因子 1；若后续服务端用量使因子上调，相同软阈值下可留容量会相应减少。

### 已有真实模型请求校验

| 获取时间测试 | 本地整份输入估算 | 服务端输入 | 服务端输出 | 服务端总量 |
| --- | ---: | ---: | ---: | ---: |
| 工具调用前 | 3,755 | 2,519 | 22 | 2,541 |
| 工具调用后 | 3,856 | 2,572 | 17 | 2,589 |

同一次用户轮次，第二次输入新增了时间调用链：本地增加 101，服务端增加 **53**。本例本地总量比真实值高约 49%～50%，说明当前短请求估算留有明显余量；**不能拿这个比例去统一折算路线 JSON、所有工具或图像**。旧历史没有逐请求真实 usage，因此其他工具的数据仍是估算。流式 usage 字段意义见 [官方 Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)。

打车预估最大的样本返回 48,899 字符，其中 `routes` 数组有 **1,069** 项，序列化后约 **47,093** 字符（约占完整结果的 96%）。所以“只有几种车型”的返回实际还带有很长的路线坐标数组，造成一次预估消耗约 23K。公交结果也包含大量路线细节。创建订单自身只有约 428，而不是最重的工具。

历史搜索范围为 109～1,605；中位数低是因为包含未找到匹配的调用，不代表搜索到多条长记录仍很便宜。搜索工具自身约 357，发现 5 个滴滴工具后还会新增约 **1,200** 的定义成本。

其余 28 种工具暂时没有实际调用样本，特别是航班、酒店、天气：可以统计定义大小，但**不能仅凭定义推断返回大小**。本文不捏造这些工具的调用成本。

## 4. 32K 大约能留多少调用、多少轮

以下是“预算内同时保留完整调用链”的粗算。固定基底按 3,712，每轮用户问句与 assistant 文字及封装统一预留 150；工具均用样本均值，打车用较大样本约 22,817。工具定义已在基底中，只额外计算发现后的定义。没计语音打断标记或额外图片，所以具体场景仍需看 Debug。

计算式：轮数约为 `floor((软阈值 - 固定基底 - 新发现的定义) / (每轮文本 + 各工具调用成本))`。同一用户轮内可能多次调用模型，但仍算一轮，不把模型请求次数混作对话轮数。

| 假设每轮流程 | 每轮新增约 Token | 32K 预算内轮数 / 工具调用数 | 64K 预算内轮数 / 工具调用数 |
| --- | ---: | ---: | ---: |
| 只聊天、无工具 | 150 | 188 轮；但先碰到独立 16K 文字阈值 | 401 轮；仍先碰到文字阈值 |
| 时间 + 定位 + 地址解析，3 次调用 | 606 | 46 轮 / 138 次 | 99 轮 / 297 次 |
| 2 次地址解析 + 1 次驾车路线 | 1,996 | 14 轮 / 42 次 | 30 轮 / 90 次 |
| 2 次地址解析 + 1 次公交路线 | 8,171 | 3 轮 / 9 次 | 7 轮 / 21 次 |
| 2 次地址解析 + 1 次较大打车预估（另载滴滴 5 定义） | 23,363 | 1 轮 / 3 次 | 2 轮 / 6 次 |
| 拍照 1 次并保留原图 | 约 1,928 | 14 轮 / 14 次 | 31 轮 / 31 次 |

打车首次发现还需约 357 的 `search_tools` 调用成本，表中没逐轮重复加；一轮同时有多次公交/预估或图像则需要叠加。打车预估的较小样本约 8K，同样预算可留约 3 轮，不能认定每次固定 23K。

**这些轮数不是 App 强制上限**：

- 原配置全输入超过 32,000 才尝试移出旧工具链，目标 24,000；现配置改为超过 64,000 时清理到 48,000，用户与模型文字继续保留。
- 当前轮 + 前 3 轮始终优先保护。未完成打车任务的最近成功预估轮、最近原图所在轮也受保护，可能在最近 4 轮之外额外保留。
- 因此 4 轮较大的打车预估就可能接近 100K，策略不会为了硬凑 32K 丢掉正在用的最近起终点。32K 是软清理触发点，不是切断最近对话的硬上限。
- 纯文字超过 16,000 才另行从旧轮卸载到 8,000，保护规则仍生效；样本每轮平均纯文字 118（含所有 assistant 文字、不含消息封装）。上表对完整轮的 150 预留与这一纯文字口径不同。
- 历史数据库始终保留完整内容，卸载仅影响发送给模型的视图。重启会话仍从空对话开始，可以工具搜索旧记录。
- 当前配置的模型容量是 1,000,000，预留输出 8,192 和安全余量 32,000，硬输入保护边界 **959,808**。模型窗口上限与软清理阈值不是同一概念，实际模型能力仍应以所选模型的服务端限制为准。

## 5. 参数建议与后续测量

目前 **16K/8K 的纯文字阈值无需因工具大而同步放大**：短语音回答的样本大约已能保存上百轮文字，不会在两三次工具调用后丢掉人说的话。

已按用户确认把全输入软阈值从 **32K/24K 调到 64K/48K**，维持文字 16K/8K 和现有保护规则。64K 能提供多一点历史工具链空间，不代表保留到 1M；也不保证四份 23K 预估全在软预算内。

比扩大阈值更值得单独评估的是：工具适配层给模型一个明确、稳定的精简返回结构，例如预估优先保留车型、价格、起终点、订单所需字段，而不是重复提供千余路线坐标。原始完整结果仍可以归档并在 Debug 查阅；这属于确定性字段投影，不是模型总结压缩。但需先确认下单依赖，不能直接删字段，本次也未修改。

后续可对公共地点跑航班、酒店、天气的只读样本，并在 Debug 累积真实 usage；按短途/长途、多结果/少结果分别统计。缓存命中影响价格与延迟，但不会把已缓存内容从模型上下文容量中扣掉。应按整份 `prompt_tokens` 看空间，不用 `total_tokens` 代替输入空间。

## 6. 复现

仓库新增 [分析脚本](../scripts/analyze-context-tokens.mjs)，读取本地数据库与接口快照，无需 API Key，不访问网络，不执行工具或订单：

```sh
node scripts/analyze-context-tokens.mjs /path/to/utalk-history.db
```

数据库副本应包含一致的 SQLite WAL 数据（在线复制时推荐 SQLite 备份或暂停写入后复制 DB/WAL）。不要把完整数据库、照片或原始对话提交 Git。脚本只输出统计与预算分类，不输出请求消息、参数值或工具结果原文。Node.js 和 SQLite CLI 是外部运行依赖。

脚本的按轮统计覆盖此次历史样本全部会话；按次统计通过“同一 assistant 后、下一条 assistant 前”匹配调用 ID 与工具名，避免不同模型请求复用 ID 导致串线。新版本估算规则或工具可见性变更后，应同步更新脚本。
